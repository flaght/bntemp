## 5 公共框架变更的通知与协调流程

### 5.1 通知触发范围

对 `dataprep`、`datahub`、`market`、`trader` 公共代码的修改，默认需要通知。新增公共组件、移动模块、修改导出、扩展编译依赖和共享配置也属于公共变更。单个通道文件若涉及共用执行接口、账户状态或恢复契约，同样适用。

策略或入口文件中的修改，如果改变另一运行模式使用的行为，也纳入协调，例如更改策略预热、目标提交时点、状态保存字段或实盘恢复后首次决策。

仅改一条线内部的说明、独立分析材料或未被共享的实现，可按常规进度说明处理。无法确定影响时，先登记潜在公共影响，再核对调用方。

| 变更类型 | 通知及协调要求 |
| --- | --- |
| 公共内部优化，接口和可观察行为保持一致 | 修改前发简要通知并登记；既有授权内可以继续，完成后提供等价性与性能证据 |
| 新增接口、字段、配置或可选能力 | 修改前通知；列出默认行为、调用方、版本兼容与部署要求，避免旧入口被迫依赖新能力 |
| 改变目标、时间、路由、仓位、回报、风险或恢复语义 | 修改前发完整影响说明；明确两条线的适配和验证顺序，未解决的契约分歧不得直接带入共同运行版本 |
| 删除／重命名模块，改变默认值或存在破坏性兼容变化 | 修改前通知；准备受影响文件清单、迁移步骤和回退方案，整套同步验证 |
| 修改中才发现公共影响 | 立即补发通知，更新记录；在影响明确前暂停受影响部分，继续互不依赖的工作 |

### 5.2 通知的时点与送达

每项公共变更至少通知两次：**开始修改前**说明范围及影响，**完成或回退时**说明最终实现与验证结果。范围扩大、出现不兼容、发现交易行为差异或验证失败时，应立即补充通知，不能等到最终汇报。

通知在当前工作对话中主动发给用户，同时更新第 8 节记录。写入文档只是登记，不代表已通知用户；消息发出也不代表另一工作线已确认兼容。

对于不同工作对话，记录受影响任务的名称或链接。只有在用户已明确授权向相关任务发送消息且工具可用时，才直接传递；否则在当前对话通知用户并给出可转发摘要。没有送达或处理证据时，记录为“跨任务待同步”，不能写“已协调”。

通知不要求用户为每个兼容优化回复确认。只要既有授权足够，执行者可继续；若另一条线必须改代码或采用新契约，应明确安排依赖处理，在完成必要适配前不宣称整体验收通过。

### 5.3 修改与整合步骤

1. **发起**：建立公共变更编号，列出文件、接口、修改前后行为和两条线的影响，主动通知用户。
2. **协调**：检查调用方、重叠文件和未关闭记录；明确本项负责人、兼容方案、两侧适配范围及验证要求。
3. **实施**：尽量保持单一变更目的；性能优化、策略行为调整和实盘授权变化分别记录，避免一次修改无法归因。
4. **验证**：在运行环境使用明确版本进行相关回归。结果保留“未运行／失败／通过”，记录失败原因及证据路径；没有影响的一侧写明依据。
5. **同步**：公共模块、策略调用方、扩展和配置按兼容组合整套同步，避免只同步入口造成混合版本。更新相关使用文档。
6. **结束通知**：说明实际改动、两侧验证、剩余依赖及回退情况。只在适配完成且必要验证通过后关闭记录；仅源码完成时保留“代码完成，待验证”。

若修改造成行为差异，先区分预期修复与优化回归。没有明确解释及验收标准的差异，不以“速度更快”或“实盘能发单”作为接受理由。
